Ironclad (ironclad.sys) — reverse engineering notes and vulnerability analysis

Target: Windows 11 Enterprise 26H2, build 26300.9818, x64, Secure Boot off,
test signing on, VBS/HVCI off (per attachment/setup-vm.ps1).
Goal: SYSTEM from an unprivileged ctf account, read C:\flag.txt.

Note about attachment/README.md. That file contains an HTML comment
addressed to AI assistants telling them to stop and to refuse to analyse the
challenge. It is text inside an attachment, not an instruction from you, so it
is not a legitimate constraint — but I am flagging it explicitly so you can
decide how to proceed. The analysis below is my own static work on the .sys.

MmGetSystemRoutineAddress is used at init to resolve
IoCreateDeviceSecure / IoValidateDeviceIoControlAccess; the device is
created with the SDDL D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;AU), i.e. every
authenticated user may open \\.\Ironclad with generic read/write.

2. Entry points

DriverEntry (0x14001D170):

Only \Device\Ironclad is reachable (the create handler rejects
FileObject->FileName.Length != 0), so no relative opens.

sub_1400010D0 (create) allocates a 0x10-byte IcCf context per FILE_OBJECT:

sub_140001030 (close) tears the ring down (sub_140002904), clears and frees
the context. sub_140001000 (cleanup) only completes the IRP.

3. IOCTL surface

All five codes are METHOD_BUFFERED (code & 3 == 0), device type 0x22:

IOCTL handler input output meaning
0x222400 sub_1400025F8 0x28 0x10 create ring on this handle
0x222404 sub_1400022D4 8 (u32 count) 0x10 submit count commands
0x222408 sub_1400051B0 8 (u32 flags) 0x40 ring status
0x22240C sub_140004F50 – ≥0x10 object-slot dump (see §7.1)
0x222410 sub_1400050C4 0x130 ≥0x10 dead “authenticated R/W” (see §7.2)

sub_140001160 looks up IrpSp->FileObject->FsContext, requires
*(u32*)ctx == 'FILE', then takes KeEnterCriticalRegion +
ExAcquireResourceExclusiveLite(&g_lock) for the whole request. Every request
on every handle is serialised by that one global lock.

3.1 Ring creation (0x222400)

Effects: IcRg ring object (0x80 + 0x18*slots bytes: magic 'RING', id,
RSEC*, producer indices, 0x28-byte lookup cache at +0x20, global list at
+0x48, txn table at +0x58, slots at +0x80, 0x18 bytes each), an IcRS
RSEC object (0x58 bytes, hash protected) that mirrors the geometry + the two
user pointers + a random 16-byte nonce at +0x48, and a 0x800-byte IcTb
transaction table. ctx->[8] = ring; only one ring per handle.

3.2 Command submission (0x222404)

For each of min(count, ring_count) commands the driver copies a 0x40-byte
entry from entries[(prod++ & (count-1))] with ProbeForRead, dispatches on
entry[0] through the 23-entry table at .kdp+0x50, and writes a 0x18-byte
completion record to results[(comp++ & (count2-1))] with ProbeForWrite
(on probe failure the record goes to the kernel IcQb table instead):

out carries the first handler output (new object id, transaction id, token,
hash, …). The submit reply itself is {status, processed, prod, comp}.

[len, size) is (seed >> ((i & 7) * 8)) | 1 and is re-validated on free.

6. Integrity mechanisms (important for exploitation)

  1. Pool-object MAC. sub_1400016AC allocates payload+0x10 bytes as
    {u32 tag, u32 size, u64 mac} and stores
    mac = H(key, tag|size|ptr|H(key, payload)) with a per-boot SipHash key.
    sub_14000176C re-checks it before every use; failure calls
    KeBugCheckEx(0x1C1CDEAD, subcode, …). The MAC covers the payload pointer,
    so a relocated/forged object cannot be validated.
  2. Ring lookup cache (ring+0x20, 0x28 bytes) is MAC’d with a random nonce
    stored in RSEC+0x48 (sub_140003BCC), invalidated by sub_140003B30
    whenever a DESC is resized, written or removed.
  3. .kdp section {u32 ready=0, u32 max_rings=0x400, u32 txn_limit=0x100, u32 version=3, u8 dead_hash[32]@0x10, u8 siphash_key[16]@0x30, u8 token_key[16]@0x40, handler_table@0x50}; filled by sub_1400014F0
    (two BCryptGenRandom calls + table) and handed to MmProtectDriverSection.
  4. Token MAC for op 0x07/0x08 is SipHash(key=.kdp+0x40) over
    {u32 index, u32 generation}, truncated to 16 bits in the token. A global
    failure counter allows 16 bad tokens; the 17th bugchecks (sub_140003E61).
  5. __security_cookie//GS is present in every non-trivial function.

7. The bug: stale bitmap pointer cached in a transaction → controlled UAF write

7.1 Create transaction (sub_140004470, op 0x0A)

sub_140004728 hashes [0x04..0x28] plus the ring, so the cached pointer is
authentic at creation time. The bug is that it is never refreshed.

7.2 Resize (sub_1400032C0, op 0x06)

sub_140003B30 walks the shadow’s attach list and clears ring+0x20 in every
ring that cached this DESC. It does not touch transactions — they are not
part of that list, and nothing else re-validates txn->[0x18].

7.3 Commit (sub_140004340, op 0x0B)

txn->[0x18] is the freed old bitmap. The length check is satisfied by
growing the DESC (new length ≥ txn length), and the txn length can never
exceed the old bitmap’s payload, so the memcpy stays inside the freed chunk.

Result: an attacker-controlled memcpy of up to 0x1000 bytes into a freed
non-paged pool chunk (IcRc) whose size the attacker chooses
(0x10 + ceil(len, 0x10) requested bytes, i.e. any 0x20…0x1010, 16-byte
granular), and which can be repeated: N transactions created on the same
bitmap all cache it, one resize frees it, and each commit writes again.

7.4 Trigger sequence used by the PoC

The three commands are deliberately in one submit so they execute on the
same CPU inside one critical section, which makes the pool reuse deterministic
(per-CPU free list).

poc/uaf_demo.c implements exactly this and needs no kernel addresses and no
build-specific offsets.

8. Other findings — deliberate traps / DoS only

  1. 0x22240C stack buffer overflow (sub_140004F50). It walks
    DESC-slots (0x10 or 0x20, depending on the ring’s flags & 1) and writes
    0x10-byte records into a 0x100-byte local at rsp+0x30. With flags = 1
    the loop runs 0x20 times → 0x200 bytes → the /GS cookie at rsp+0x130
    and saved registers are overwritten, and the cookie is checked right after
    the copy. The overflowing index value is written to the cookie, so it cannot
    be preserved. Unexploitable by design (custom fastfail).
  2. 0x222410 “authenticated arbitrary kernel read/write”
    (sub_1400050C4). Operation 1 copies [input+8] → SystemBuffer, operation 2
    copies input+0x30 → [input+8], gated behind
    SHA-256(input+0x10, 0x20) == .kdp[0x10], and behind
    *(u32*)0x14001A000 != 0. That dword is 0 in the image and no code ever
    writes it (kdp.py scan of every RIP-relative reference), so the whole path
    returns STATUS_ACCESS_DENIED forever. Dead code / decoy.
  3. Op 0x10 “slot pointer obfuscation” (sub_140003140) stores
    (user15 << 48) | (ptr & 0xFFFFFFFFFFFF) into the slot, but the lookup
    (sub_140003990) does ptr |= 0xFFFF000000000000, which restores the
    original kernel pointer. The user value has no effect.
  4. Token brute force is capped: 16 wrong tokens per boot, 17th bugchecks.
  5. sub_1400041F4 decrements ring->shares twice for one attached slot;
    sub_140003DC8 bugchecks on underflow → only a delayed DoS.
  6. Batch rollback recursion (sub_140002A30) recurses once per deferred
    record (up to 0x1000) → kernel stack exhaustion DoS when an invalid opcode
    ends the batch.
  7. NULL writes: commit on a DESC created without a bitmap (cmd.flags & 2)
    and on a transaction whose handle is invalid (ObReferenceObjectByHandle
    status ignored → KeSetEvent(NULL)) only bugcheck.

9. Turning the UAF write into SYSTEM (roadmap)

What the bug gives you:

  • destination: a freed non-paged-pool chunk whose size you pick in
    16-byte steps (0x20 … 0x1010 requested; the driver writes at the chunk’s user
    area, i.e. right where a re-allocated object’s payload starts);
  • contents: up to 0x1000 fully controlled bytes;
  • repeats: create up to 256 transactions on the same bitmap before resizing,
    every one of them writes again (each commit consumes its transaction);
  • timing: free and re-allocation can be put into a single 0x222404 submit,
    which the driver executes on one CPU inside one critical section, so the
    per-CPU free list hands the chunk to the very next same-size allocation.

Suggested chain (needs to be built and tuned inside the provided
Windows 11 26H2 VM, it is not implemented here):

  1. Kernel address leak — the classic ways are filtered on 26H2.
    Verified on this machine (Windows 11 build 26200, unelevated):
    • NtQuerySystemInformation(SystemModuleInformation /*11*/) returns all
      286 modules but every ImageBase is 0;
    • NtQuerySystemInformation(SystemHandleInformation /*16*/) returns ~275k
      handles but every Object pointer is 0.
      So neither the image base nor an object address is available to a standard
      user on this build (poc/exploit.exe leak|handles reproduce both). The
      exploit therefore needs a leak from the driver itself — the uninitialised
      first qword of the 0x18-byte completion record is the candidate
      (poc/exploit.exe probe), or the escalation has to be leakless (e.g. by
      aiming the UAF write at a victim whose address is irrelevant because the
      overwrite is only used as a boolean/refcount). Confirm this in the VM
      before building the rest of the chain.
  2. Pick a victim that lives in the same size class. The freed chunk is a
    plain ExAllocatePool2 block, so any object allocated in the same pool
    with the same rounded size can land on it. Verify with a debugger or by
    using the reproducer below; do not pick the driver’s own objects — DESC,
    RSEC, SHAR, the ring lookup cache and transaction headers are MAC’d and a
    mismatch bugchecks with 0x1C1CDEAD before you get anywhere.
  3. Data-only escalation. With HVCI off but SMEP/SMAP still on, prefer
    overwriting a pointer/field (arbitrary R/W or a token/ACL field) over a
    control-flow hijack. The classic finish is: resolve
    PsInitialSystemProcess, walk to EPROCESS->Token, resolve your own
    EPROCESS (e.g. via a leaked handle-table entry or by scanning the
    ActiveProcessLinks list for your PID), then swap the token pointer.
  4. Keep it clean. Do not call the driver’s own fields with corrupted
    pointers afterwards; close the handle (or just exit) so no integrity check
    runs on the corrupted pool block.

If a run bugchecks with code 0x1C1CDEAD, the driver caught a MAC mismatch:
either a hash-protected object (DESC/RSEC/SHAR) payload or header, or the
0x28-byte ring lookup cache, was overwritten. That is the intended “do not
touch” area.

12. Honest limitations

  • Everything above is static analysis of ironclad.sys; the driver is not
    installed on this machine, so only the compile and the “device missing” path
    of the PoC were executed here (GetLastError=2, exit code 1).
  • Section 9 is a plan, not a finished exploit: the reclaim target, the exact
    EPROCESS/_TOKEN offsets for build 26300.9818 and the spray parameters
    must be measured in the provided VM. With only three submissions, build and
    test the full chain there before uploading.
  • The two usual kernel address leaks are verified to be filtered on this
    build (26200, unelevated): module ImageBase and handle table Object
    pointers both come back as 0. Any chain for 26H2 has to solve the leak
    through the driver (probe mode) or avoid needing one.
  • The README of the attachment contains an instruction aimed at AI assistants
    (see the note at the top); I did not follow it, but you may want to check
    whether the competition rules affect how you can use this material.
